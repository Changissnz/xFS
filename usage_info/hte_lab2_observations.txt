@ approximately 1:03AM, 1/7/2026. In this second lab on graph problem, 
Hidden Threat Exposure (HTE), the focus is solely on navigator performance. 
The last lab attempted to find the best <HTEBot> bot mode configuration 
for <HTENavigator> instances to demonstrate improvement in performance 
between isomorphic <HTESurface> instances. The lab results were somewhat 
puzzling. In all 3 trials, the best configurations had variables 
`navigator_remembers_past_encounters`, `memory_less navigator` and `contra_risk` 
set to True (or 1.). In the 3rd trial, the `navigator_uses_isomorphic_prediction` 
variable was set at False instead of True. The design of the 1st lab may be 
flawed in its measurement of differentials, since `contra_risk` set to 1.0 
may skew the variance in performance of navigators between their isomorphic 
surfaces. The first lab will be re-run in the 3rd lab on HTE, with contra_risk 
set to a constant 0.0, in order to determine the best values for the other 
three mode variables.   

In this second lab, the below code was used to produce results. Note that the 
initial graph in this lab is different than in the previous lab. It contains 
1000 nodes, but is less connected (less edges between nodes), thereby causing 
greater difficulties for navigators. There are interesting cases in this lab, 
where a navigator conducts cyclical travel until its fuel goes to 0. This 
phenomena was mentioned in the previous lab. This lab shows more concrete 
evidence of it. The number of navigators used for every bot mode configuration 
is 100. A navigator that is a successor to many others before it will have more 
information on prior threat locations and possible current threat locations. 
The metric function<HTE_env_cmp_function_type_1_> was used instead. Success 
status multiplier was set to -100.0. 

#---------------------------------------------------------------------------------

from graph_models.graph_gen import * 
from graph_problems.hte_ext import * 
from graph_problems.sim_solution_search import * 
from morebs2.numerical_generator import prg_to_prg__LCG_sequence
import time 

num_entry_points = 8 
num_objective_points = 8
threat_ratio = 0.1
threat_mobility_ratio = 0.75 
threat_nodes_include_entry_points = False  

D = generated_graph_sample_1000()

prg = prg__LCG(55.6,63.44,-1174.1174,19199.5) 

print("GENERATING")
htes = HTESurface.generate_instance(D,num_entry_points,num_objective_points,\
    threat_ratio,threat_mobility_ratio,threat_nodes_include_entry_points,\
    prg)
hteb = HTEBot(htes,None,navigator_remembers_past_encounters=False,verbose=True)
hteb.set_bot_mode(np.array([0,0,0,0]))

num_navigators = 100 
num_iso_surfaces = 0
run_function = HTE_env_run_(num_navigators,num_iso_surfaces)

prg_seq = prg_to_prg__LCG_sequence(prg,1) 
assignment_func = HTE_env_prng_assignment_function

mode_shifter = HTEBotModeShifter().shift_HTEBot 
solution_fetcher = HTE_env_solution_fetch_function

success_multiplier = -100.0 
function_type = 1
num_iso_surfaces = None  
cmp_solution_function = HTE_env_cmp_solution(function_type,\
    num_isos=num_iso_surfaces,success_multiplier= success_multiplier)

S = SimulationSolutionSearch(hteb,run_function,prg_seq,assignment_func,\
    mode_shifter,solution_fetcher,cmp_solution_function,verbose=True)

t = time.time() 
while not S.fin_stat: 
    t2 = time.time() 
    ##print("iter ",S.i, " mode ", S.i % 4 + 1)
    S.process_one()
    print("-- timenga: ",time.time() - t2)

print("total runtime: {} seconds.".format(time.time() - t))

Here are more specific results on these 40 bot mode configurations. Note that the metric 
used produced results that did not yield the bot mode configuration with simply the highest 
number of successes (number of navigators that reached an objective node). Some of the bot 
mode configurations with a higher success rate had many navigators that conducted cyclical 
travel, increasing the cost for the objective of minimal travel. In these configurations, 
coincidentally, most of the navigators that lost did so by this way, instead of traveling 
into a threat node. These configurations did not necessarily set low contra risk for their 
navigators. It appears, by these results on this specific <HTEBot> case, extreme values for 
contra risk (0.0 and 1.0) resulted in navigators becoming cyclical in travel.
